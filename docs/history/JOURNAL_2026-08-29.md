## 3. The image append — RUNNING ON CRON

Attaches images 2..N from our Cloudinary account to the ~2,039 Scope 1 products
that currently hold only the hero.

**Expected work: 23,307 images.** That is 25,514 uploaded for Scope 1, minus the
2,207 heroes already attached.

**Cron (fires :00 and :30):**

```
0,30 * * * * /bin/bash /home/u222311468/domains/slategrey-falcon-350174.hostingersite.com/gvssync_append.sh --confirm-attach
```

**Estimate: overnight.** Earlier I said two days; that assumed the per-firing
scan would eat most of the 25-minute window. The 03:19 run measured the fast
scan at 30 seconds for 4,747 products. Append's scan is heavier — page size drops
100 → 8 and each page pulls up to 60 media rows — so 6–10 minutes, leaving 15+
minutes per window for attaching.

**The run is idempotent.** It reads each product's existing media filenames,
compares them against the Cloudinary journal, and attaches only the difference.
An interrupted run costs the time spent and nothing else; the next firing
recomputes what is still missing. Nothing is ever attached twice.

**The guard that matters.** A product qualifies only if at least one of its
existing media filenames matches a public_id from our journal. A Scope 2 product
— still carrying Salsify hash filenames — scores zero matches and is skipped by
construction. There is no SKU list to maintain and no way to forget one.

## 5. Reversal — read before undoing anything

### 5a. Stop the append (seconds, safe, no data loss)

Create an empty file named `STOP`, no extension, in:

```
…hostingersite.com/jmv_sync/logs/STOP
```

The run halts at the next product. **Delete it before restarting**, or every
future run stops immediately. Then delete the cron entry in hPanel if you want it
stopped for good.

### 5b. Un-attach appended images — NO BULK UNDO EXISTS

Be aware of this before deciding. Shopify admin cannot bulk-delete individual
media rows, and `--verify` only purges media that FAILED to fetch — it will not
remove healthy images. Reversing an append means writing a tool that walks the
affected products and deletes media by filename.

It is at least *identifiable*: every appended image carries our public_id as its
filename (`bathroom-vanities-…-<sku>-<n>.webp`), and `logs/images_repaired_*.csv`
lists every SKU touched, per run, with a timestamp. So a reversal is buildable —
it is just not a button.

**Practical consequence:** if the morning log shows the guard misfiring and
galleries duplicating, stopping early matters far more than deciding what to do
next. Create the STOP file first, diagnose second.

### 5c. Remove the 271 products

Shopify admin → Products → filter **Vendor: James Martin**, sort by Created,
select those created 2026-08-29, Bulk actions → Delete. Cross-check the selection
against the 271 handles in `the271_import_report.csv` before confirming.

Deleting the product deletes its media with it, which also reclaims that ~0.9 GB.

### 5d. Roll back the PHP

Rename `jmv_fix_images.php.bak` back over `jmv_fix_images.php`. The old build
cannot do append mode at all, so this is also a way to neutralise the cron
without touching hPanel — though 5a is cleaner.
