# BVO Brand Onboarding — Playbook

> Step-by-step playbook for adding a new brand to the catalogue.

**How to take a brand from RFLPos + GVS into BathroomVanitiesOutlet.com.**

Written 2026-09-05, immediately after the ER Vanities load (78 SKUs). It is a
record of what worked, in what order, and — more usefully — of every trap that
cost time, so the next brand does not pay for them again.

Direction matters: `SHOPIFY_IMPORT_BRIEF.md` covers loading supplier feeds
**into** GVS/Shopify. This covers pulling **out** of RFLPos and GVS **into**
BVO. Do not confuse the two.

Next brands in line: **Atlanta Vanity**, **Nearmé**.

---

## 0. Before anything — what is authoritative for what

The single most common way to waste a day is to take a fact from the wrong
system. Fix this in your head first.

| Fact | Authority | Never take it from |
|---|---|---|
| Sync key, price basis, stock | **RFLPos export** | anywhere else |
| Images, image order | **GVS/Shopify product JSON** | a CSV export (see trap 9) |
| Attributes, materials, finishes | **The owner, asked directly** | inference, vendor copy |
| Dimensions | **Manufacturer drawings**, else the owner | sibling products (trap 12) |
| Product copy | **Generated by us, gated** | vendor copy (duplicate-content risk) |
| Taxonomy, brand string, slugs | **BVO** | RFLPos or Shopify |

RFLPos is **read-only, always**. Its brand strings, titles and SKUs are its own.
Map them on the way in — never "fix" RFLPos to match BVO.

## 2. Phase 1 — crosswalk

**Goal: one verified identifier joining every BVO product to its RFLPos record.**
Inventory sync is worthless without it, and a stale quantity is worse than none
because it sells stock you do not have.

- The join field is `products.rflpos_item_id` = RFLPos **SKU**.
- Export from RFLPos: SKU, Product, Brand, Category, Selling Price, Current stock.
- Expect two SKU shapes. ER had 71 as `PR####` and 7 where the long vendor code
  *is* the SKU. Both are valid — do not "normalise" them.
- Verify 100% resolve before proceeding. Anything unresolved is a stop.

**Known limitation, accepted on ER:** RFLPos SKU is an editable text field. If
someone renames one, the link breaks silently. The durable key is RFLPos's
integer product id, which is not in the standard export. Decide per brand
whether to carry both.

## 3. Phase 2 — images

### The mechanic that makes this cheap

Cloudinary **fetches the bytes itself** from a URL you give it. Nothing transits
your server. Both CDNs cap on request, so Cloudinary receives an already-compliant
file and you need no image library anywhere.

- Google Drive: `lh3.googleusercontent.com/d/<id>=s2048` — caps the **long edge**
- Shopify: `<url>?width=2048` — caps the **width only**
- Neither upscales. Shopify **ignores** `&format=jpg` (verified: returns PNG, same bytes)

### Free-plan limits that actually bite

| Limit | Value | Note |
|---|---|---|
| Max megapixels | 25 MP | London masters are 29 MP and bounce |
| Max file size | **10 MB** | **checked on FETCH, before any transform** |
| Admin API | 500 req/hr | Upload API is unlimited |
| Credits | 25/mo | 1 credit = 1 GB storage *or* 1 GB bandwidth *or* 1,000 transforms |

**Trap 1 — the 10 MB ceiling applies to what Cloudinary FETCHES.** `f_jpg` cannot
rescue an oversized source, because the source is refused before the transform
runs. Carry a fallback ladder: retry at `width=1600`, then 1200, then 900, scoped
to the size error only.

**Trap 2 — `c_limit` preserves the source format.** A PNG source stays a PNG at
close to full weight; the first ER run stored a 9,417 KB render. The incoming
transform must be `c_limit,w_2048,h_2048,f_jpg,q_auto:good,b_white`. `b_white`
matters: alpha PNGs flatten onto black without it.

**Trap 3 — storage is not the constraint people assume.** 390 MB reads as
alarming but is under half a credit against 25. Measure before reacting. The real
cost of oversized masters is the six that fail outright, not the bytes.

**Trap 4 — `overwrite=false` freezes a public_id forever.** Get the naming right
first. A swap later is delete-then-reupload, and a failed delete followed by a
requeue silently keeps the old asset — so only rewrite the journal when zero
deletes failed.

**Trap 5 — public_ids must be slug-safe: no dots.** `29.5` is not valid. Use the
nominal ladder (23.5→24, 29.5→30, 35.5→36, 41.5→42, 47.5→48, 59.5→60, 71.5→72).
Make sure the ladder has an entry for **every** size present, including malformed
ones — ER shipped 7 ids reading `59s`/`59d` because `59` had no ladder entry.

**Trap 6 — Media Library placement comes from `asset_folder`,** not from slashes
in the public_id.

### Run procedure — image import to Cloudinary

This is the part that actually moves the pictures. Nine steps, and the order is
not negotiable: two of them are irreversible.

**Files, and where each one lives**

| File | Repo (Mac) | Server |
|---|---|---|
| `bvo_cloudinary_push.php` | repo root | `jmv_sync/` |
| `bvosync_cloudinary.sh` | repo root | **domain root** (beside `gvssync.sh`) |
| `<B>_cloudinary_map.csv` | `data/` | `jmv_sync/state/` |
| journal (written by the tool) | — | `jmv_sync/state/bvo_cloudinary_journal.csv` |
| log | — | `jmv_sync/logs/bvo_cloudinary.log` |

**1 — Credentials, once per Cloudinary account.** Add to
`hbuilds/config/.env` on the server only:

```
CLOUDINARY_CLOUD_NAME=
CLOUDINARY_API_KEY=
CLOUDINARY_API_SECRET=
```

Nowhere else. Never on a command line. Confirm the cloud name by eye — a typo
gives `Invalid cloud_name` on every row, and it is easy to misread
(`bathroom-vanities-outlet` has hyphens).

**2 — Validate the map as data, before it can freeze anything.** The push
script's gate checks: ids unique, slug-safe, ≤70 chars, no malformed hyphens,
every row has a source URL, alt text present, a known crop rule, and every
`reference` row pointing at a real `yes` row. A bad id here is permanent.

**3 — Push and deploy.**

```
cd "<repo>" && bash git_push_bvo_cloudinary.sh
```

**4 — Copy to the server after the deploy lands.** `jmv_sync/` and the domain
root are outside the deploy tree:

```
cp hbuilds/current/nodejs/bvo_cloudinary_push.php      jmv_sync/
cp hbuilds/current/nodejs/data/<B>_cloudinary_map.csv  jmv_sync/state/
cp hbuilds/current/nodejs/bvosync_cloudinary.sh        ./
chmod +x bvosync_cloudinary.sh
```

**5 — Dry run.** Uploads nothing. hPanel → Cron Jobs, temporary every-minute cron:

```
/bin/bash <domain-root>/bvosync_cloudinary.sh --dry-run
```

Read `jmv_sync/logs/bvo_cloudinary.log`. Confirm the row count, and that every
source line shows a **capped** URL (`=s2048` for Drive, `?width=2048` for
Shopify). An uncapped source is a >25 MP rejection waiting to happen.

**6 — Pilot a handful before the full run.**

```
/bin/bash <domain-root>/bvosync_cloudinary.sh --only=<Collection> --limit=5 --confirm-upload
```

Then **look at them in the Cloudinary console** — not at the log. Check format
(JPEG, not PNG), file weight (hundreds of KB, not thousands), and that alpha
has flattened to white rather than black. Pick the easiest collection to
eyeball: square, product-on-white.

**7 — The rest.**

```
/bin/bash <domain-root>/bvosync_cloudinary.sh --confirm-upload
```

Re-running is safe: `overwrite=false`, and any row already `ok` in the journal
is skipped. The tool self-limits at 25 minutes and resumes.

**8 — Report, and read it properly.**

```
/bin/bash <domain-root>/bvosync_cloudinary.sh --report
```

Wanted: `ok = <n>, failed = 0`. Investigate every failure individually —
`File size too large` means the fallback ladder ran out, which means that source
is genuinely unusable and needs new photography.

**9 — Delete the cron.** It fires every minute and there is nothing left to do.

**Verify one delivery URL in a browser** before calling it done:

```
https://res.cloudinary.com/<cloud>/image/upload/w_300/<public_id>.jpg
```

**If you have to replace an asset later:** public_ids are frozen, so it is
delete-then-reupload. Delete via the Admin API in batches of 100, only rewrite
the journal when **zero** deletes failed, then re-run `--confirm-upload`. A
failed delete followed by a requeue silently keeps the old image, and the log
will tell you it succeeded.

### Dedupe

Check for one file shared across many SKUs before uploading. One ER showroom
photo appeared on 14 SKUs; uploading it 14 times would have meant 14× storage and
14 derivative sets. Upload once, reference the rest.

## 4. Phase 3 — manuals

Different shape from images, for one reason: **a PDF on disk has no URL**, so
Cloudinary cannot fetch it. The bytes must be POSTed, which means the files have
to reach the server. That is the only reason they do.

- Endpoint is `/raw/upload`, not the image endpoint.
- Keep PDFs **out of git.** 63 MB of binaries in a repo that auto-deploys on every
  push is a cost paid forever, for files that change never.
- **Trap 7 — Cloudinary blocks PDF delivery by default on new accounts.** The
  upload succeeds, the asset shows "Blocked for delivery", and the console preview
  errors with `show_original_customer_untrusted`. Fix: Settings → Security → allow
  delivery of PDF and ZIP files. Do this *before* the upload run to save a cycle.
- Delivery URL: `https://res.cloudinary.com/<cloud>/raw/upload/<public_id>.pdf`
  (the `.pdf` works even though the public_id has no extension).

**Trap 8 — verify you are uploading the rebranded artwork.** The ER manuals were
uploaded twice: the first run used the original folder rather than the rebranded
one, and it was only caught because the owner opened a PDF. **Checksum the staging
folder against the intended source before the run**, not after.

---

### Run procedure — manual import to Cloudinary

Same wrapper pattern, different endpoint. Deltas from the image run only:

**0 — Turn on PDF delivery FIRST.** Cloudinary → Settings → Security → *Allow
delivery of PDF and ZIP files*. Skipping this means uploading, discovering every
asset says "Blocked for delivery", and doing it again.

**1 — Checksum the staging folder against the intended source.** This is the
step that was skipped on ER and cost a full delete-and-reupload cycle:

```
for f in "<staging>/"*.pdf; do
  b=$(basename "$f")
  [ "$(md5 -q "$f")" = "$(md5 -q "<intended-source>/$b")" ] || echo "MISMATCH $b"
done
```

**2 — Create `jmv_sync/manuals/` on the server** and put the PDFs in it.
Filenames must match the map exactly — the map joins on filename.

**3 — Files:** `bvo_manuals_push.php` → `jmv_sync/`, `bvosync_manuals.sh` →
domain root, `<B>_manual_map.csv` → `jmv_sync/state/`.

**4 — Dry run, then `--confirm-upload`, then delete the cron.** Same as images.
`skipped` must be 0 on the dry run; anything else means a stale journal — delete
`jmv_sync/state/bvo_manuals_journal.csv` and re-run.

**5 — Open one PDF in a browser** and check the *artwork*, not just that it
loads. `https://res.cloudinary.com/<cloud>/raw/upload/<public_id>.pdf`

23 files at ~2.7 MB each finish in about 15 seconds.

## 5. Phase 4 — attributes

This is the phase that determines whether the listing is thin or complete.
Benchmark against the James Martin feed: 195 columns is what "complete" looks
like.

### How to ask

One question at a time. Give the column, what it means, and a small set of
concrete options with a recommendation. Use **SKIP / ANSWER** as the skip verb —
never yes/no, which collides with the column's own Yes/No values.

Batching questions does not save time. It produces answers that cannot be matched
to questions, and then the whole set has to be re-asked.

### Where each value goes

Three destinations, and putting a value in the wrong one makes it invisible:

1. **`products` columns** — `width_in`, `color`, `color_family`, `product_type`,
   `prop65`, `warranty`, `country_origin`, `ships_ltl`, `upc`, `freight_class`,
   `height_in`, `depth_in`, `component_role`, `vendor_sku`, `status`
2. **`product_attribute_values`** (EAV, `attr_key` + `value_text`/`value_num`) —
   everything the sidebar filters on
3. **`attribute_definitions`** — the filter must be *defined* or the EAV rows are
   invisible. This is how `vanity_type` became an orphan.

**Trap 9 — style is multi-value.** One EAV row per canonical bucket, never a
comma-joined string. This works because migration 011 dropped the composite
primary key on `product_attribute_values` and added a surrogate `id`. Under the
older 005 schema a second `style` row for the same product would fail.

**Trap 10 — some filters are defined but never populated.** `country_origin` and
`ships_ltl` have `attribute_definitions` rows, but the JM importer writes them
only to `products` columns, so both filter groups render empty for ~6,000
products. If you want the filter to work, write **both**: the column is canonical,
the EAV row is a filter index.

**Never guess a material or a compliance value.** A mistaken construction claim is
the one that draws a lawsuit. Gate it mechanically: every material word must
appear either in that SKU's own source copy or on an owner-authorised list.

## 6. Phase 5 — copy

Generate it; never inherit vendor copy. Duplicate content is an SEO liability and
vendor copy carries claims you cannot substantiate.

Three rules, **enforced by a gate in the build script, not by care**:

1. **No price.** Not a figure, not a range, not "additional cost". Prices change;
   the copy does not.
2. **No unsourced material claim.** Checked against the SKU's own source terms
   plus the authorised global list.
3. **Feature then benefit.** A spec never appears without what it means for the
   buyer. People buy on emotion, not specs.

Also caught by gates worth keeping: unsubstantiated superlatives, and competitor
disparagement — "the wobble every cheap vanity develops" trips the price-word gate
for good reason.

**Trap 11 — use word boundaries in every text gate.** Substring matching cost time
twice: `Bright White` contains **right**, and `splashes` contains **ash**. Both
produced confident false positives. `\bright\b`, not `right`.

**Trap 12 — the nominal size ladder needs an entry for every size token,
including non-numeric component codes.** Without it the raw code is printed with
an inch mark: *"Bristol Bridge3DE″ bathroom vanity"* — shipped-quality copy that
also called every component a bathroom vanity.

Convention that emerged and is worth keeping: **`name` carries the actual size
(29.5″), body copy carries the nominal (30″).**

## 7. Phase 6 — pricing

Two separate calculations.

**Retail uplift**, to cover free shipping — banded off the RFLPos price:

| RFLPos price | Uplift |
|---|---|
| under $500 | +$150 |
| $500 – $900 | +$350 |
| $901+ | +$450 |

**Compare-at price** — `price × 1.42`, then rounded **up** to the next value
ending `49.99` or `99.99` (every multiple of 50, minus a cent):

```python
def ladder(x):                      # x is a Decimal
    n = ((x + Decimal('0.01')) / 50).to_integral_value(rounding=ROUND_CEILING)
    return n * 50 - Decimal('0.01')
```

The `+0.01` matters: it keeps a price already sitting on a rung where it is,
while moving 2350.00 up to 2399.99 rather than back to 2349.99.

The displayed discount then varies (ER: 29.6%–34.6%, median 30.4%) because
rounding adds a variable amount. **That variation is intentional** — it reads as
a per-product markdown rather than a flat across-the-board one.

## 8. Phase 7 — Google Merchant Center

`applyGmcDefaults()` in `src/utils/seoDefaults.js` derives most GMC fields
server-side on insert. **Do not assume that covers you.**

**Trap 13 — `google_product_category` is keyed off `product_type` via
`GMC_CATEGORY_MAP`.** If the brand's `product_type` values are not keys in that
map, every product loads with a NULL category and Google rejects the feed. ER's
three values (`Vanity`, `Bridge Unit`, `Linen Tower`) were all absent. Either add
them to the map or set the category explicitly per row.

**Trap 14 — `custom_label_4` reads `products.model`.** If the load file has no
`model` column, collection-level bid rules have nothing to group on. Set
`model` = collection.

**Trap 15 — column name mismatch.** The load file calls it `meta_description`;
the `products` column is `meta_desc`. Map it in the SQL.

MPN convention established on ER, worth reusing:

```
Collection-BucketSize+suffix-3letterColour
    Kensington-30L-DOK          L/R/D/S run straight onto the number
    Bristol-24-3dr-NWA          word-like suffixes are hyphenated
```

Hyphenate word-like suffixes — `243dr` scans as two-hundred-forty-three. Give
**every non-vanity a form suffix** (`3dr`, `1dr`, `MU`, `LC`) so a future vanity
at the same bucket width can never collide with a component. Check for duplicate
MPNs before loading: Google treats brand + mpn as a product identifier.

Also set: `google_condition` = new, `age_group` = Adult, `identifier_exists` = 1
when an MPN exists even with no GTIN.

## 9. Phase 8 — the review sheet

**Build it, and make the owner read it before the load.** The ER review caught
six real defects that had passed every automated gate:

- two Bristol bridges titled 84″ that are 24″ units
- all five components with broken copy and the wrong product noun
- four SKUs whose `width_in` and `name` did not follow a size correction
- GMC category that would have been NULL on every row

Requirements, learned the hard way:

- **One row per SKU, every field**, not ten separate files
- **XLSX, not CSV.** Long descriptions contain embedded newlines; a plain CSV
  viewer shifts every row and the header appears to vanish
- Frozen header rows and SKU column, autofilter, colour-banded column groups
- **A Legend tab that says which blanks are correct.** Without it every
  intentional gap reads as an omission and gets re-litigated
- **Regenerate it from source with a script** (`build_review.py`), so a correction
  in the source file never has to be re-applied by hand

## 10. Phase 9 — the load

**BVO has a products export route but no import route.** The load is SQL through
phpMyAdmin. There is no way around this.

Before writing a line of it, run a **read-only diagnostic** answering:

1. Do these SKUs already exist? (insert vs update — `slug` is UNIQUE)
2. What brand string is actually in use?
3. Do the collection rows exist, and under what brand? (`collections.brand`
   defaults to 'James Martin')
4. Would any slug collide?
5. What `product_type` vocabulary is live *today*? Loading a pending taxonomy
   early makes every product invisible to the current sidebar filter.

Target tables: `products`, `product_images`, `product_attribute_values`,
`product_bullets`, `product_documents`, `product_components`,
`product_shipping_boxes`, `product_certifications`, `product_accessories`.

Do not duplicate a relationship across two tables. Component pairings live in
`product_components`; mirroring them into `product_accessories` is the
two-homes-for-one-fact problem Rule 10 exists to stop.

## 11. Infrastructure notes

- **Deploy**: `git push origin main` → Hostinger rebuilds `hbuilds/current/`.
- **`jmv_sync/` and the domain root are OUTSIDE the deploy tree.** Anything
  landing there needs a manual `cp` after each deploy. Scripts at repo root
  deploy to `hbuilds/current/nodejs/`.
- **There is no SSH.** Server-side scripts run via **hPanel → Cron Jobs**. Create
  a temporary every-minute cron, read the log, delete the cron.
- **Cron kills every process at 30 minutes.** Self-limit at 25 and resume from a
  journal written after every row.
- **Cron does not inherit hPanel's injected environment variables.** Read `.env`
  from disk; fail loudly naming every path tried.
- **Credentials come from `.env`, never inline.** A hardcoded secret at the domain
  root is wiped every time the file is re-copied after a deploy.
- Never put a credential on a command line — arguments appear in process listings
  and error text.
- `device_bash` cannot delete files. Move them to `_to_delete/` instead.

## 12. GVS listing hygiene — check before trusting an export

These are all real, all found on GVS, and all silently corrupt a mapping:

- **Duplicated listings keep "copy"** in the handle: `-copy` suffix or
  `copy-of-` prefix. The `copy-of-` form is worse — it preserves the *original*
  product's name, so the handle says 36 when the title says 35.5, or single when
  it is double, or still carries a retired brand name.
- **Internal codes leak into titles.** "SFD" appeared in 9 ER titles.
- **A title's number may be the assembled run, not the unit.** "Bristol 84 in.
  (3 Drawer Bridge)" is a 24″ unit in an 84″ run. An importer reading width from
  that title is wrong by 60 inches.
- **Trap 16 — an export can be category-scoped and silently omit listings.** The
  ER export was missing the Kensington 29.5 Left listing entirely because it and
  its Right sibling sit in different categories. A missing listing looks exactly
  like a SKU with no photos. If a SKU appears to have no images, check the live
  store before concluding anything.
- **L/R pairs sharing identical photos** is common and usually means one side has
  no photography of its own. Check the filename — `Kensington-30R-WH` tells you
  which side is actually pictured.

Read images from the **live product JSON** (`/products/<handle>.js`), not the CSV.
It gives real dimensions and the true merchandising order, and it cannot be stale.
Image 1 is the hero — preserve that order.

## 14. What to do differently next time

Ordered by how much time it would have saved on ER.

1. **Read the briefs at session start.** Half the corrections in the ER load were
   me acting on a reconstruction instead of checking what was in front of me — an
   invented folder path, a skipped step, the wrong source folder for the manuals.
2. **Pull the export you actually need, once, unfiltered.** A category-scoped
   export cost a full detour.
3. **Turn on Cloudinary PDF delivery before the manual run**, not after.
4. **Settle the public_id naming before the first upload.** They freeze.
5. **Ask the owner for component dimensions up front.** Components share neither
   the height nor the depth of the vanities they sit beside — inferring them was
   wrong on every value.
6. **Build the review sheet earlier.** It caught defects that all the automated
   gates missed, because some errors are only visible to someone who knows the
   products.
7. **One step at a time, and say where each runs** — Mac, server, phpMyAdmin,
   browser. A step list without locations is not a step list.
