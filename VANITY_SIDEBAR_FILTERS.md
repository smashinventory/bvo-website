# VANITY SIDEBAR FILTERS — THE GOVERNING DOCUMENT

**Status:** signed off by Sam, 2026-09-15.
**Governs:** which filter groups appear in the vanity collection sidebar, in
what order, and how that order is enforced.
**Supersedes:** every code comment, commit message and push-script epilogue
that states a different order. Several of those existed and were wrong; see
§7.

---

## 1. THE ORDER

Top to bottom, on every vanity collection page:

| # | Group | Source of options | Query param |
|---|---|---|---|
| 1 | **Size** | `availableSizes` → `SIZE_BUCKETS` (±2" bands) | `size_in` |
| 2 | **Cabinet Color** | `cabinet_finish` colour swatches | `color_family`, `color_exact` |
| 3 | **Configuration** | the four canonical `product_type` values | `type` |
| 4 | **Vanity Style** | EAV `attr_key='style'` — ⚠ see §5 | `style` |
| 5 | **Brand** | `availableBrands` | `brand` |
| 6 | **Price Range** | min/max inputs | `min_price`, `max_price` |

**Nothing else.** Not Hardware Finish, not Vanity Type, not Mount Type, not
Door Style, not Number of Drawers, not Sink Type, not Countertop Material,
not Countertop Included. Those definitions still exist in
`attribute_definitions` and several are still `is_active = 1`; they are held
back by an allow-list in the template, not by the database.

Through an ordering widget, 2026-09-15, after two earlier attempts failed:

## 2. BRAND IS FIFTH HERE AND FIRST EVERYWHERE ELSE

This is the single most error-prone fact in this area.

- **Faucets, mirrors, accessories, tops:** Brand renders **first**, at the
  top of `collection.ejs`, as it always has.
- **Vanities:** that top call site is **skipped**, and Brand is included
  again at position 5.

Brand therefore has **three call sites** and one definition:

```
views/partials/filters/brand.ejs          ← the only definition

collection.ejs  <% if (!isVanityCategory) { %>            ← non-vanity, first
collection.ejs  <% if (isVanityCategory && !_isModelGroup) { %>  ← vanity grid, fifth
collection.ejs  (inside the model-group block)            ← vanity model-group, fifth
```

**If you add a fourth render path, it needs its own Brand call site.**
Forgetting one does not misplace Brand — it deletes it from that page
entirely. That is exactly what shipped in `78afb2a` and had to be fixed in
the commit after it.

`vanity-style.ejs` is a partial for the same reason.

## 3. TWO RENDER PATHS — BOTH ARE VANITIES

`collection.ejs` contains two complete sidebars. Which one runs is decided
by `categories.display_mode`:

| Path | `display_mode` | Example URL | Cabinet Color comes from |
|---|---|---|---|
| **grid** | anything else | `/collections/bathroom-vanities` | inside `attributeDefs.forEach` |
| **model-group** | `model-group` | `/collections/vanity-models` | its own explicit block |

Both are `isVanityCategory = true`. **Both must produce the §1 order.**

The template guards on `_isModelGroup`:

```ejs
<% var _isModelGroup = (typeof displayMode !== 'undefined' && displayMode === 'model-group'); %>
```

### Where the order is actually decided

Two banner comments, one per path. Search for them:

- `APPROVED VANITY ORDER (Sam, 2026-09-15)` — model-group
- `APPROVED VANITY ORDER, GRID PATH (Sam, 2026-09-15)` — grid

**Editing block order anywhere else changes nothing on the live page.**

### The grid path's non-obvious constraint

On the grid path Cabinet Color renders *from inside* `attributeDefs.forEach`.
So to put it second, **Configuration, Vanity Style and Brand must sit AFTER
that loop.** They originally sat before it, which is why the live page read

```
Size | Configuration | Vanity Style | Cabinet Color | Price Range
```

There is no way to place Cabinet Color second while those three precede the
loop. Do not try to "tidy" them back above it.

## 4. SIZE — WHY IT IS NOT ATTRIBUTE-DRIVEN

Size is the most-used filter on the site. It renders **explicitly**, gated
only on `availableSizes.length`, and deliberately does **not** depend on an
`attribute_definitions` row.

It used to. Migration 010 (`b70bc67`, 14 Jul) contains:

```sql
DELETE FROM attribute_definitions
WHERE attr_key = 'size_in' AND category_id = 1
  AND id = (SELECT MAX(id) FROM (SELECT MAX(id) AS id FROM attribute_definitions
            WHERE attr_key = 'size_in' AND category_id = 1) t);
```

No `COUNT(*) > 1` guard. Run twice, it deletes the only remaining row. An
identical statement targets `sink_count`. Both rows are gone from production
today — confirmed 2026-09-15: they do not appear in the active-facets query.

The filter had vanished, heading and all, while `availableSizes` sat fully
populated one variable away. It cost about a week to find.

**Rules that follow:**

- Size renders from `availableSizes`, never from a definition row. Gate G4
  proves it renders with `attributeDefs: []`.
- **Always expanded.** Every pick reloads the page; a group that starts
  collapsed shuts itself on every tick. Picking three sizes meant reopening
  it three times.
- **Multi-select**, with a badge counting active buckets.
- **Only populated buckets appear** (CLAUDE.md Rule 10) — `getAvailableWidths`
  runs the page's filters *without* `size_in`.
- **S/D suffixes**: `60S` / `60D` when a bucket holds both configurations.
- `name="size_in"` is load-bearing — megamenu Shop-By-Size chips and
  bookmarked `?size_in=` URLs depend on it.

Migration 010's two unguarded DELETEs are **still unguarded**. See
`OPEN_ITEMS.md`.

## 5. ⚠ VANITY STYLE DOES NOT FILTER

**Position 4 is rendered and reserved. The filter is inert.**

`collectionsController.js` never reads `req.query.style`. Grep the whole
file for `style` and you get **zero hits**. Ticking a box posts
`?style=Modern`; the controller discards it; the page reloads unchanged.

The data exists:

- `importJamesMartinFeed.js` writes `attr_key='style'` rows
- `lookbookController.js:46` reads `req.query.style` correctly

Only the collection path is unwired. This is CLAUDE.md rule 5 — written,
stored, **not read**.

It is rendered anyway, on purpose, so the approved position is settled and
visible rather than silently dropped. It is labelled inert in
`views/partials/filters/vanity-style.ejs` and in the template banner.

**Do not describe this filter as working.** Wiring it is a separate,
approved piece of work — it needs a join in the model-group query and a
parse in the grid path.

## 6. HOW THE ORDER IS ENFORCED

Gates live in `git_push_retire_unused_facets.sh`. Fixtures live in
`tests/fixtures/collectionLocals.js` — one file, shared, so gates cannot
disagree about what they are testing.

| Gate | Asserts |
|---|---|
| **G4** | Size renders with no definition row, always open, multi-select, Rule 10 |
| **G5** | No filter-group heading appears **twice** on any rendered category |
| **G8** | Every `VANITY*` fixture matches §1 **exactly**; Brand still first on non-vanity; no vanity-only group leaks sideways; **fails if fewer than 2 VANITY fixtures exist** |
| **G10** | Every human-readable statement of the order — script header, script epilogue, numbered blocks in the template — matches G8's `WANT` array |

### The rule these encode

**Render the page. Do not read the source.**

An earlier G5 counted `size_in` inputs in the source, found 2, and reported
"one for the standard grid, one for model-group". True of the source, false
of the page: both blocks were gated on data the model-group render supplies,
so **both fired**, and the sidebar showed Size twice — once as checkboxes,
once as chips, both posting `size_in`. Configuration was doubled the same
way. Counting blocks cannot detect this. Only rendering can.

### The other rule

**Cover every combination, or say which ones you did not.**

G8 originally rendered vanity+model-group and faucets+grid. The broken
combination — **vanity+grid**, the page Sam actually uses — was rendered by
no gate. Every gate was green while Brand was missing from the live site.

Two fixtures across four combinations *reads*, in a green summary, exactly
like coverage.

## 8. IF SAM ASKS FOR A DIFFERENT ORDER

1. Get the order **from Sam**, in his own words or via a widget he submits.
   Do not infer it.
2. Update `WANT` in G8.
3. Update **both** banner comments in `collection.ejs`.
4. Move the blocks. On the grid path remember §3 — anything that must
   precede Cabinet Color has to go before `attributeDefs.forEach`, and
   anything after it goes after the loop.
5. Update the push-script header and epilogue. G10 will fail until you do.
6. Update §1 of this document.
7. Run the gates, then **break each one deliberately** and confirm it fails
   for the intended reason. A negative test that fails for the wrong reason
   is not a pass — report it as inconclusive.
8. Push, then **restart the Node process in hPanel**. Hostinger auto-deploys
   on push to `main` but does **not** restart Node. Without the restart the
   old template stays in memory and it looks like the push did nothing.

### The eight facets retired 2026-09-15

`is_active = 0`, **not deleted** — reversible with one UPDATE:

`ships_ltl`, `country_origin`, `primary_material`, `ada_compliant`,
`assembly_required`, `mount_type`, `sink_included`, `drawer_side`

They were never *added*. They were seeded months ago by migrations 002/003
and never rendered, because `getAllAttributeValues()` was throwing MySQL
`#1271` (illegal mix of collations) on every call and returning `{}` from a
bare `catch`. No checkbox or boolean facet could appear anywhere on the
site. `f9596b2` fixed that function and all of them surfaced at once — the
vanity sidebar went from 7 groups to 15 overnight, which is what started
this whole piece of work.

Five of the eight are `category_id = NULL`, i.e. global. Retiring them
cleared vanities, mirrors, faucets and accessories together.
